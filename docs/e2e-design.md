# E2E Test Design: สั่งซื้อและชำระเงินสินค้าในตะกร้า

E2E ด้วย Playwright เทสเฉพาะ **critical user journey** ผ่านหน้าเว็บ `http://localhost:5173` (React, `src/client`) ที่ต่อกับ backend `http://localhost:3000` และ database จริง ส่วนกฎย่อยอยู่ในระดับ Unit และ API ซึ่งแยกจากเอกสารนี้

| ไฟล์ | หน้าที่ |
|---|---|
| [`e2e/checkout.spec.ts`](../e2e/checkout.spec.ts) | test script รันบน chromium, firefox, webkit |
| [`e2e/helpers.ts`](../e2e/helpers.ts) | reset ข้อมูลก่อนเทส, ตรวจผลใน backend, ขั้นตอนหน้าเว็บที่ใช้ซ้ำ |

## วิธีรัน

```bash
npx playwright test                       # ทุก browser (Playwright เปิด backend และ frontend ให้เอง)
npx playwright test --project=chromium    # chromium อย่างเดียว
npx playwright test --ui
npx playwright show-report
```

- `.env` ต้องมี `SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET` และ `TEST_PASSWORD` (รหัสผ่านของ `cus_normal` และ `admin01`)
- `workers: 1` เพราะทุกเทส login เป็น `cus_normal` และเขียน database เดียวกัน ระหว่างรันห้ามใช้บัญชีนี้ทดสอบมือ
- ก่อนทุกเทส `resetTestData` ตั้งราคา stock และสถานะสินค้ากลับเป็นค่าตั้งต้น ยกเลิก order ที่รอชำระเงิน และล้างตะกร้า จากนั้นตรวจว่า**ตะกร้าว่างและไม่มี order ค้าง**ก่อนเริ่ม

## 2. Test case

ทุก TC มี precondition ร่วม: backend และ frontend ทำงานอยู่ ข้อมูลอยู่ที่ค่าตั้งต้น ตะกร้าของ `cus_normal` ว่าง และไม่มี order รอชำระเงิน

| ID | SC | Test case | Input | Expected output |
|---|---|---|---|---|
| TC-01 | SC-01 | ซื้อ Coffee Beans 2 ชิ้นแล้วชำระเงินสำเร็จ | login `cus_normal`, เพิ่ม P1 2 ครั้ง, กรุงเทพฯ + ส่งแบบปกติ, สร้างคำสั่งซื้อ, ยืนยันชำระเงิน | ค่าจัดส่ง ฿40 ยอดสุทธิ ฿940 / หน้า "ชำระเงินสำเร็จ! คำสั่งซื้อ #…" ตะกร้าเป็น 0 / backend: order "ชำระเงินสำเร็จ" stock P1 = 18 ตะกร้าว่าง / ประวัติแสดง order นั้น |
| TC-02 | SC-02 | ชำระเงินไม่สำเร็จ | login, เพิ่ม P1 1 ครั้ง, ต่างจังหวัด + ส่งด่วน, สร้างคำสั่งซื้อ, จำลองชำระเงินไม่สำเร็จ | ค่าจัดส่ง ฿120 ยอดสุทธิ ฿570 / กลับหน้าตะกร้า Coffee Beans ยังอยู่ / backend: order "ชำระเงินไม่สำเร็จ" ตะกร้ามี P1 = 1 stock P1 = 20 |
| TC-03 | SC-03 | ยกเลิกคำสั่งซื้อที่รอชำระเงิน | login, เพิ่ม P1 1 ครั้ง, ต่างจังหวัด + ส่งด่วน, สร้างคำสั่งซื้อ, ยกเลิกคำสั่งซื้อ | ค่าจัดส่ง ฿120 ยอดสุทธิ ฿570 / กลับหน้าตะกร้า Coffee Beans ยังอยู่ / backend: order "ยกเลิก" ตะกร้ามี P1 = 1 |
| TC-04 | SC-04 | เปิดตะกร้าว่าง | login, กด "ตะกร้าสินค้า 0" | "ตะกร้าสินค้าของคุณยังว่างอยู่" ไม่มีปุ่ม "ดำเนินการชำระเงิน" / backend: จำนวน order เท่าเดิม |
| TC-05 | SC-05 | รหัสผ่านผิด | `cus_normal` / `wrong-password` | แสดง `AUTH_INVALID_CREDENTIALS` "Invalid username or password" ยังอยู่หน้า login |
| TC-06 | SC-05 | ไม่มีชื่อผู้ใช้นี้ | `no_such_user` / `wrong-password` | เหมือน TC-05 (ไม่บอกว่าผิดที่ชื่อหรือรหัส) |

TC-01 ใช้ กรุงเทพฯ + ส่งแบบปกติ ส่วน TC-02 และ TC-03 ใช้ ต่างจังหวัด + ส่งด่วน เพื่อให้ครอบทั้งสองพื้นที่และสองความเร็ว

TC-05 กับ TC-06 แบ่งตาม Equivalence class ของข้อมูล login ที่ invalid: ชื่อผู้ใช้มีอยู่แต่รหัสผิด และชื่อผู้ใช้ไม่มีอยู่

## 4. Script

[`e2e/checkout.spec.ts`](../e2e/checkout.spec.ts) มีคอมเมนต์เลขขั้นตรงกับตาราง test steps ทุกขั้นมี `expect` และหา element ด้วย `getByRole` / `getByLabel` / `getByText` ตามข้อความจริงในหน้าเว็บ ขั้น C1 และ C2 อยู่ใน `goToCheckoutUI` และ `createOrderUI` ของ [`e2e/helpers.ts`](../e2e/helpers.ts)

เลข order ที่ตรวจใน backend คือเลขที่หน้าเว็บแสดงหลังกด "สร้างคำสั่งซื้อ" จึงยืนยันได้ว่าสิ่งที่ผู้ใช้เห็นตรงกับที่ระบบบันทึก

ถ้าพบ defect ที่ยังแก้ไม่ได้ ให้ใส่ `test.fail(true, 'DEF-…')` ในเทสนั้นไว้ชั่วคราว ชุดเทสจะยังเขียว เมื่อแก้แล้ว Playwright จะรายงาน "expected to fail but passed" ให้ลบ `test.fail()` ออก

## Defects ที่พบ

| ID | Defect | สถานะ |
|---|---|---|
| DEF-01 ถึง DEF-07 | หน้าเว็บรุ่นก่อน: ไม่มีช่องคูปอง ไม่มีให้เลือกการจัดส่ง ตะกร้าไม่ sync กับ backend หน้า checkout ไม่เรียก API ไม่มีปุ่มชำระเงินไม่สำเร็จ ประวัติไม่ดึงจาก backend | ✅ แก้แล้วในหน้าเว็บรุ่นปัจจุบัน |
| DEF-08 | ตาราง `orders` มี `orders_zone_check` รับ `inCity`, `upcountry`, `remote` แต่โค้ดและ API.md ใช้ `bangkok`, `upcountry` สร้างคำสั่งซื้อแบบกรุงเทพฯ จึงตอบ 500 | ✅ แก้ constraint แล้ว |
| DEF-09 | ตาราง `orders` มี `orders_status_check` รับ `รอชำระเงิน`, `ชำระเงินแล้ว`, `ยกเลิก` แต่โค้ดใช้ `ชำระเงินสำเร็จ` และ `ชำระเงินไม่สำเร็จ` ชำระเงินจึงตอบ 500 ทั้งสำเร็จและไม่สำเร็จ | ✅ แก้ constraint แล้ว |

SQL ที่ใช้แก้ DEF-08 และ DEF-09 ใน Supabase SQL Editor:

```sql
alter table orders drop constraint orders_zone_check;
alter table orders add constraint orders_zone_check
  check (zone in ('bangkok', 'upcountry'));

alter table orders drop constraint orders_status_check;
alter table orders add constraint orders_status_check
  check (status in ('รอชำระเงิน', 'ชำระเงินสำเร็จ', 'ชำระเงินไม่สำเร็จ', 'ยกเลิก'));
```

ถ้าสร้าง database ใหม่ (เช่น Supabase โปรเจกต์อื่นสำหรับ CI) ต้องรัน SQL นี้ด้วย ไม่อย่างนั้น TC-01 และ TC-02 จะล้ม

**สรุป:** critical user journey ทั้ง 5 scenario ทำงานถูกต้องตาม spec ทั้งหน้าเว็บ backend และ database บน 3 browser
