# E2E Test Design: สั่งซื้อและชำระเงินสินค้าในตะกร้า

E2E ด้วย Playwright เทสเฉพาะ **critical user journey** ผ่านหน้าเว็บ `http://localhost:5173` (React, `src/client`) ที่ต่อกับ backend `http://localhost:3000` และ database จริง ส่วนกฎย่อยอยู่ในระดับ Unit และ API ซึ่งแยกจากเอกสารนี้

| ไฟล์ | หน้าที่ |
|---|---|
| [`e2e/checkout.spec.ts`](../e2e/checkout.spec.ts) | test script รันบน chromium, firefox, webkit |
| [`e2e/helpers.ts`](../e2e/helpers.ts) | reset ข้อมูลก่อนเทส, ตรวจผลใน backend, ขั้นตอนหน้าเว็บที่ใช้ซ้ำ |

## วิธีรัน

```bash
npx playwright test                       # ทุก browser (Playwright เปิด backend และ frontend ให้เอง)
npx playwright test --project=chromium    # chromium อย่างเดียว
npx playwright test --ui
npx playwright show-report
```

- `.env` ต้องมี `SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET` และ `TEST_PASSWORD` (รหัสผ่านของ `cus_normal` และ `admin01`)
- `workers: 1` เพราะทุกเทส login เป็น `cus_normal` และเขียน database เดียวกัน ระหว่างรันห้ามใช้บัญชีนี้ทดสอบมือ
- ก่อนทุกเทส `resetTestData` ตั้งราคา stock และสถานะสินค้ากลับเป็นค่าตั้งต้น ยกเลิก order ที่รอชำระเงิน และล้างตะกร้าใน backend จากนั้นตรวจว่า**ตะกร้าว่างและไม่มี order ค้าง**ก่อนเริ่ม ตะกร้าในหน้าเว็บว่างเสมอ เพราะแต่ละเทสเปิด browser ใหม่

## 2. Test case

ทุก TC มี precondition ร่วม: backend และ frontend ทำงานอยู่ ข้อมูลอยู่ที่ค่าตั้งต้น ตะกร้าของ `cus_normal` ว่าง และไม่มี order รอชำระเงิน

| ID | SC | Test case | Precondition เพิ่ม | Input | Expected output |
|---|---|---|---|---|---|
| TC-01 | SC-01 | ซื้อ Coffee Beans 2 ชิ้นแล้วชำระเงินสำเร็จ | — | login `cus_normal`, เพิ่ม P1 2 ครั้ง, ดำเนินการชำระเงิน, ยืนยันสั่งซื้อและชำระเงิน | หน้า "ชำระเงินสำเร็จ! คำสั่งซื้อ #…" ตะกร้าเป็น 0 / backend: order นั้น "ชำระเงินสำเร็จ" stock P1 = 18 ตะกร้าว่าง / ประวัติแสดง order นั้น |
| TC-02 | SC-02 | ชำระเงินไม่สำเร็จ | — | login, เพิ่ม P1 1 ครั้ง, ดำเนินการชำระเงิน, ชำระเงินไม่สำเร็จ | ตะกร้ายังเป็น 1 / backend: order "ชำระเงินไม่สำเร็จ" ตะกร้ามี P1 = 1 stock P1 = 20 |
| TC-03 | SC-03 | ยกเลิกที่หน้า checkout | — | login, เพิ่ม P1 1 ครั้ง, ดำเนินการชำระเงิน, กลับไปตะกร้าสินค้า | หน้าตะกร้ามี Coffee Beans ฿450.00 / backend: order "ยกเลิก" ตะกร้ามี P1 = 1 |
| TC-04 | SC-04 | เปิดตะกร้าว่าง | — | login, กด "ตะกร้าสินค้า 0" | "ตะกร้าสินค้าของคุณยังว่างอยู่" ไม่มีปุ่ม "ดำเนินการชำระเงิน" / backend: จำนวน order เท่าเดิม |
| TC-05 | SC-05 | รหัสผ่านผิด | — | `cus_normal` / `wrong-password` | แสดง `AUTH_INVALID_CREDENTIALS` "Invalid username or password" ยังอยู่หน้า login |
| TC-06 | SC-05 | ไม่มีชื่อผู้ใช้นี้ | — | `no_such_user` / `wrong-password` | เหมือน TC-05 (ไม่บอกว่าผิดที่ชื่อหรือรหัส) |

TC-05 กับ TC-06 แบ่งตาม Equivalence class ของข้อมูล login ที่ invalid: ชื่อผู้ใช้มีอยู่แต่รหัสผิด และชื่อผู้ใช้ไม่มีอยู่

## 4. Script

[`e2e/checkout.spec.ts`](../e2e/checkout.spec.ts) มีคอมเมนต์เลขขั้นตรงกับตาราง test steps ทุกขั้นมี `expect` และหา element ด้วย `getByRole` / `getByLabel` / `getByText` ตามข้อความจริงในหน้าเว็บ

- ผลฝั่ง backend ตรวจด้วย soft assertion (`expect.configure({ soft: true })`) ถ้า backend ผิด เทสจะยังเดินหน้าเว็บต่อจนจบ แล้วรายงานทุกจุดที่ผิดในครั้งเดียว
- TC ที่ล้มเพราะ defect ที่รู้แล้วใส่ `test.fail(true, 'DEF-…')` ไว้ ชุดเทสจึงยังเขียว เมื่อแก้ defect จนเทสผ่าน Playwright จะรายงาน "expected to fail but passed" ให้ลบ `test.fail()` ออก

## 5. ผลการรัน

รันวันที่ 2026-11-03 บน chromium, firefox และ webkit: **18 passed (4.4 นาที)** ผลเหมือนกันทุก browser ใน 18 ตัวนี้ มี 9 ตัวที่ผ่านจริง และ 9 ตัวที่ล้มตรงตาม `test.fail()`

| TC | ผล | จุดที่ล้ม (ตรวจจากการรันแบบไม่มี `test.fail()`) |
|---|---|---|
| TC-01 | ❌ ตามคาด (DEF-04) | หน้าเว็บผ่านทุกขั้นถึงขั้น 7 แต่ขั้น 5 backend ไม่มี order ใหม่ ขั้น 6 ไม่มี order เลขที่หน้าเว็บแสดง stock P1 ยังเป็น 20 และตะกร้าใน backend ยังมี P1 = 2 |
| TC-02 | ❌ ตามคาด (DEF-04, DEF-06) | ขั้น 3 backend ไม่มี order ใหม่ ขั้น 4 ไม่มีปุ่ม "ชำระเงินไม่สำเร็จ" |
| TC-03 | ❌ ตามคาด (DEF-04) | หน้าเว็บผ่าน (ของยังอยู่ในตะกร้า) แต่ backend ไม่มี order ทั้งตอน checkout และตอนยกเลิก |
| TC-04 | ✅ | — |
| TC-05 | ✅ | — |
| TC-06 | ✅ | — |

## Defects ที่พบ

| ID | Defect | ผลกระทบ | TC |
|---|---|---|---|
| DEF-04 | ปุ่ม "ดำเนินการชำระเงิน", "กลับไปตะกร้าสินค้า" และ "ยืนยันสั่งซื้อและชำระเงิน" ไม่เรียก API (OP-8, OP-9, OP-10) หน้าเว็บสร้าง order ปลอมใน browser และสำเร็จทุกครั้ง | ไม่มี order จริง stock ไม่ถูกตัด ตะกร้าใน backend ไม่ถูกล้าง | TC-01, TC-02, TC-03 |
| DEF-06 | หน้า checkout ไม่มีทางทำรายการชำระเงินไม่สำเร็จ (OP-11) | ทดสอบ SC-02 ผ่านหน้าเว็บไม่ได้ | TC-02 |
| DEF-07 | หน้าประวัติคำสั่งซื้อใช้ข้อมูลใน browser ไม่เรียก `GET /orders` | ประวัติแสดง order ที่ไม่มีใน backend | TC-01 ขั้น 6–7 |
| DEF-08 | `POST /orders/new/payment` (OP-8) ตอบ 500 ทุกครั้ง: database ไม่รับ `zone: "bangkok"` (`orders_zone_check`) | ถึงแก้ DEF-04 แล้ว ก็ยังสร้าง order ไม่ได้ | จะเห็นใน TC-01 ถึง TC-03 หลังแก้ DEF-04 |
| DEF-01 | หน้าตะกร้าไม่มีช่องใส่คูปอง (OP-6) | ใช้คูปองผ่านหน้าเว็บไม่ได้ | ไม่อยู่ใน 5 scenario |
| DEF-02 | หน้า checkout ไม่มีให้เลือกพื้นที่และความเร็วในการจัดส่ง คิด VAT 7% และ "ส่งฟรี" แทนค่าส่งตาม spec | ยอดสุทธิไม่ตรง spec | ไม่อยู่ใน 5 scenario |
| DEF-03 | ปุ่ม +/−, ลบ และล้างตะกร้าในหน้าเว็บไม่เรียก API (OP-4, OP-5) | ตะกร้าในหน้าเว็บกับ backend ไม่ตรงกัน | ไม่อยู่ใน 5 scenario |

ตรวจค่า `zone` ที่ database ยอมรับใน Supabase SQL Editor:

```sql
select conname, pg_get_constraintdef(oid) from pg_constraint
where conrelid = 'orders'::regclass and contype = 'c';
```

**สรุป:** หน้าเว็บพาผู้ใช้ผ่านเส้นทางซื้อของได้ แต่ไม่มีอะไรถูกบันทึกใน backend (DEF-04) และถึงจะต่อ API แล้ว backend ก็ยังสร้าง order ไม่ได้ (DEF-08) ส่วนที่ทำงานถูกต้องคือ login (สำเร็จและผิด) การใส่ตะกร้า และการกันตะกร้าว่างไม่ให้ checkout
